# ---------- A → B → C：同一个 22 通道 V7 模型，三段只换数据 ----------
# ============================================================================
# 🔴 **三段共用一个模型**（`--v7 1`，22 通道）：
#   A 段 board 级 `full.npz`（人类着法 one-hot）
#     → B 段同一份 `full.npz` + `soft_index`（软 CE）
#       → C 段 `stdata_v7` 分片（KataGo 搜索分布内建）
#   权重用 `--model` 逐段承接（`load_state_dict` strict 零缺失，已由
#   `tests/test_v7_single_model.py::test_weights_carry_from_board_level_to_packed_stage` 钉住）。
#
#   ⚠ 参数量有**两个**值（2026-10-06 实测 `build_katago_v7_net()`）：
#     · 5,562,121 = 纯 nbt 参考结构（`gau_positions=None, gau_first_nbt=gau_last_nbt=0`）
#     · 5,759,497 = **当前 cfg 默认**（中部 6 块的 `inner.1` 换成 GAU）
#     两者的键集不同（共有 264 个），**互相 load_state_dict 会报错**。
#     GAU 是 2026-10-06 的在途改动（`katago_v7.py` 尚未提交，预算测试
#     `tests/test_katago_v7_budget.py` 当时红 7 条），跑前先确认落盘的是哪一种。
#
# 为什么 A/B 也能用 V7：`load_from_path(--v7 1)` 按**数据布局**分派 ——
#   含 `spatial_packed` → `V7PackedDataset`（预算好的 22 平面）
#   含 `boards`        → `V7Dataset`（训练时实时算 22 平面，`feature_v7.spatial_channels_v7`）
#   两者喂给模型的张量形状**逐位相同** ⇒ 权重可承接。此前 A/B 落在 12 通道
#   父类上，V7 的 22 平面根本没参与，是本条链最大的静默错误。
#
# ⚠ 逐段**必须**显式承接，不要指望自动续训：三段的 policy 口径不同
#   （one-hot → 软 CE → stdata 软 CE + value/futurepos/ownership），
#   LR 与 epoch 也各自独立。
# ⚠ B 段**必须加 --soft-only-sampling 1**：软 CE 是逐行二选一（mask=0 的行贡献
#   恰好 0，不退化成 one-hot）。不加 ⇒ 只有约 1% 的行吃软标签、99% 喂 0，
#   policy 去折中而不是学搜索。`--soft-weight 0` **关不掉**这个问题。
# ⚠ C 段**不需要** `--soft-index`：stdata 每行自带 `policy_player_prob` /
#   `policy_opp_prob`，归一化后直接就是软标签（`--policy-loss soft_ce` 照写即可）。
# ⚠ 910A 无 BF16 → 必须 fp16 + GradScaler；`--scaler-init-scale` 给 1024
#   （正式默认 65536 在大 batch 下会炸）。NPU 上 `--compile` 无效，别加。
# ⚠ 预取 worker 是**每 rank** 的：2 卡 × 12 = 24，4 卡 × 6 = 24（实测 CPU 甜点）
# ⚠ LR 跟有效 batch 走：LR = 0.00356 × √(有效batch / 2500)
# ⚠ `--export-onnx` 对 V7 **无效**（走 `GoAI` 的 12 通道推理链）；V7 导出见第 7 步
# ⚠ 落盘文件名带 `.latest`：`--out models/x.pth` ⇒ 实际存 `models/x.pth.latest`

# 🔴 `--attention-dropout` 默认 0.1 会**盖掉 V7 的设计值 0.0**：
#   `katago_v7.py` 写明「**没有 dropout**」且 `NBT_TF_CFG['attn_dropout']=0.0`，
#   但 `train_sft.py:4221` 把 `attn_dropout=args.attention_dropout` 传了进去
#   （0.1 是 12 通道 SE 网的默认，`build_katago_se_net(attention_dropout=0.1)`）。
#   实测（非测试，直接实例化）：
#     --attention-dropout 0.1 -> MHSA.attn_dropout = [0.1]   ← 不给该 flag 就是这个
#     --attention-dropout 0.0 -> MHSA.attn_dropout = [0.0]
#     attn_dropout=None       -> MHSA.attn_dropout = [0.0]   ← 纯设计意图
#   ⇒ **V7 每次训练实际都开着 0.1 的注意力 dropout**，与 docstring 相反。
#     ✅ 已拍板（2026-10-06）：上面六条 A/B/C 命令**显式给 `--attention-dropout 0`**
#     对齐设计意图（V7 docstring 明确「没有 dropout」，0.1 是 12 通道 SE 网默认串味）。
#     根修（把 train_sft.py 对 V7 不再透传该 flag，或默认改 0）留给后续改动，
#     在那之前命令必须带着它。续训承接旧 checkpoint 不受影响（dropout 非权重）。
#   附带后果：`backbone.py:1646` 是 `use_online = _attn_online and dropout_p == 0.0`，
#     dropout 归 0 后 `--attn-online 1` 不再静默空转（本文件仍默认不给它，理由见上）。
#
# ⚠ `--attn-online {0,1}`（默认 0）：手写 math 注意力改 online-softmax（flash 风格），
#   不物化 (Nq,Nk) 分数矩阵 ⇒ 反向不保留它、省显存。与 materialize 路径**数值等价但
#   非逐位相同**（fp32 `max|Δ|≈7e-07`），开了会让
#   `test_twelve_channel_path_bit_identical` 基线失效 ⇒ 默认关，要开先跑
#   `pytest tests/test_online_softmax_attn.py`。真机加速比尚未实测。
#   注意它只在 `--attention-dropout 0` 时才真正生效（见上一条 🔴）。
#
# ⚠ `--use-sdpa {0,1}`（默认 1，2026-10-06 从环境变量 GOAI_SDPA 搬成 CLI 参数）：
#   NPU 注意力内核总开关。1 = 放开 CANN 融合 SDPA（F.scaled_dot_product_attention）：
#   相比手写 math 大幅降注意力开销，且内部 fp32 累加、比 fp16 手写 math 更不易溢出
#   （顺带缓解 warmup 后 NaN）。受 `_sdpa` 内部 batch 上限保护（B>60000 自动回退
#   math）；旧 CANN（<8.0.RC3.20）/ torch_npu<2.1 / SDPA API 缺失时也自动回退。
#   0 = 强制所有后端回退手写 math（调试数值差异 / 旧 CANN 兼容）。
#   默认 1 与原 GOAI_SDPA 默认行为一致 ⇒ 下面六条命令**不显式给**（留痕见核对表）。
#   （flash-attn 独立库只在 CUDA Ampere+ 上参与（A100 优先，--flash-attn 默认 1），
#     NPU 路径不用它。）
#
# batch 与 LR（实测/推导，不是拍的）
#   LR = 0.00356 × √(有效batch / 2500)，有效batch = batch × 卡数 × accum
#   六条命令逐一核对（全部与公式一致）：
#     A-1 / C-1  2800×1×1 = 2800  → 0.00377
#     C-2        2800×2×1 = 5600  → 0.00533
#     A-2 / B / C-3  1000×4×2 = 8000 → 0.00637
#
# ⚠ 「batch 2000/卡 OOM ⇒ 4 卡定档 1000」（第 204 行附近）与 A-1/C-1 的
#   **单卡 batch 2800** 并存，两者看不出能同时成立（每卡显存不该随卡数变化）。
#   按 `v7_batch_memory_advice` 的公式，block 级 checkpoint 开启时
#   4.65 MB/样本 ⇒ 64 GB × 0.9 预算下 batch 上限过万，1000/2800 都远不到边；
#   关掉 checkpoint 则 278 MB/样本、batch 上限只有 200 出头 ⇒ 「2000 必 OOM」
#   那条更像**没有 block checkpoint 时**的实测。而 A-1/C-1 标的「✅ 已用 64 行

#   两半**互相脱钩**，导致 A、B 两种结构各自撞在不同的一半上：
#     ① 键校验这半：`export_checkpoint` 用 `build_katago_v7_net()` 的键集当 want
#        （katago_export.py:522-529）—— 那是**当前 cfg（GAU 开）**的 306 个键。
#          · 纯 nbt 老 checkpoint（324 键，无 gau）→ 报「缺 42 个张量，例如
#            blocks.3.inner.1.gau.k.weight」→ **导不出**
#     ② 组装这半：`_build_trunk` 把每个 inner 单元**硬编码**成
#        `attn(.norm_attn/.attn)` + `ffn(.norm_ffn/.ffn)` 两件套
#        （katago_export.py:276-301），压根不看模型实际建了什么。
#          · GAU 开的 checkpoint（306 键，`inner.1` 是 gau 而非 attn）→ 过了键校验，
#            但卡在 `_t('blocks.3.inner.1.norm_attn.weight')` → **也导不出**
#   ⇒ 不是「checkpoint 没训好」，是**导出器没跟上 GAU 改动**。修法二选一：
#        (a) 让 ① 用与 ② 同源的布局来校验（先把 GAU 排除在导出之外），
#        (b) 给 `_build_trunk` 补上 GAU 的映射 —— 见下一条，官方格式**没有这个原语**。
#
# 🔴 官方 modelVersion 17 的 trunk 只有 **5 种块类型**，没有 GAU：
#     ordinary_block / gpool_block / nested_bottleneck_block /
#     transformer_attention_block / transformer_ffn_block
#     （本仓实现见 `src/data/katago_bin.py:1547-1604`，kind 分发全表就这 5 个）
#   ⇒ GAU（`GatedAttentionBlock`，9 个权重张量/单元）**无法原样进官方格式**，
#     要导出只能：把 GAU 那 6 个内块降级回 attn+ffn（丢权重），或另立 modelVersion。
#   这是**结构决策**，不是代码 bug，需要拍板后再动导出器。
#
#   当前 .bin.gz 是 GAU 之前导的（`tmp/coding/a_v7_npu4.bin.gz`，20,138 KB，
#   modelVersion 17 / 22 in / 19 global / 11 块 × 4 内件，引擎可加载）。
#   ⚠ 它与**当前 cfg 的模型不同构**，拿现在的 `build_katago_v7_net()` 去加载它会报错。
