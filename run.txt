# ---------- 2. ★ A → B → C：三段 SFT（同一个 22 通道 V7 模型，只换数据）----------
# ============================================================================
# 🔴 三段**共用一个模型**，权重用 `--model` 逐段承接（strict 零缺失）：
#   A 段 board 级 full.npz（人类着法 one-hot）
#     → B 段同一份 full.npz + soft_index（KataGo 软 CE）
#       → C 段 data/stdata/ 分片（搜索分布内建）
#   由 `tests/test_v7_single_model.py::test_weights_carry_from_board_level_to_packed_stage` 钉住。
#   A/B 能用 V7 的原因：`--v7 1` 按**数据布局**分派 —— 含 spatial_packed → V7PackedDataset，
#   含 boards → V7Dataset（实时算 22 平面）。两者喂模型的张量形状逐位相同 ⇒ 权重可承接。
#
# ⚠ 逐段**必须**显式 `--model` 承接，不要指望自动续训：三段 policy 口径不同
#   （one-hot → 软 CE → stdata 软 CE + value/futurepos/ownership），LR/epoch 各自独立。
# ⚠ A/B 段**必须** `--games-npz`：不给 ⇒ 贴目按 0 ⇒ 全局 ch5（currentSelfKomi/20）
#   恒 0、ch18 三角波走偏。19 维里有 2 维依赖贴目，sidecar 里 90.30% 的局有真贴目，
#   不接等于扔掉 9 成信息，**且不报任何错**（loss 照降、指标照报）。
# ⚠ B 段**必须** `--soft-only-sampling 1`：软 CE 是逐行二选一，不加则只有约 1% 的行
#   吃软标签、99% 喂 0，policy 去折中而不是学搜索。`--soft-weight 0` 关不掉这个问题。
# ⚠ C 段**不要** `--games-npz`（贴目已在行里）、也**不需要** `--soft-index`
#   （stdata 每行自带 policy_player_prob/policy_opp_prob，归一化即软标签）。
# ⚠ 落盘带 `.latest`：`--out models/x.pth` ⇒ 实际是 `models/x.pth.latest`。
#
# ---- 参数为什么是这些值 ----
# LR = 0.00356 × √(有效batch / 2500)，有效batch = batch × 卡数 × accum
#   2800×1×1 = 2800 → 0.00377 ｜ 2800×2×1 = 5600 → 0.00533 ｜ 1000×4×2 = 8000 → 0.00637
# batch：V7 的 22 通道特征在训练时**不再实时计算**（分片里已预算并位打包），
#   iterLadders 那 99.8% 的 CPU 开销在 V7 上不存在 ⇒ batch 可比 12 通道大。
#   预取 worker 是**每 rank** 的：1 卡×24 / 2 卡×12 / 4 卡×6 = 24（实测 CPU 甜点）。
# ⚠ `--scaler-init-scale` / `--scaler-growth-interval` 已从下面命令里删掉，因为
#   **910B 自动走 BF16，而 BF16 下 `use_scaler=False` —— GradScaler 根本不会被创建**，
#   这两个参数是死参数（`run.txt` 第 21-24 行记着 2026-10-06 的实测结论）。
#   ⚠ **但换 910A 就必须加回来**：910A 走 FP16、`use_scaler=True`，此时不给就是
#   代码默认 0.0 = PyTorch 的 65536，大 batch 下必炸（fp16 未来点平方溢出 65504）。
#   910A 上给 `--scaler-init-scale 1024 --scaler-growth-interval 100000`
#   （growth 调大 = 关掉自动增益，防震荡）。
#   启动日志里 `[启动] amp_dtype=… scaler=…` 那行会直接告诉你走的是哪条 —— 别靠猜。
# 🔴 `--attention-dropout 0` **必须显式给**（代码默认 0.1）：
#   0.1 是 12 通道 SE 网的默认值，会经 `train_sft.py` 透传进 V7，覆盖掉
#   `NBT_TF_CFG['attn_dropout']=0.0`——而 katago_v7.py 明确写「**没有 dropout**」。
#   实测：不给该 flag 时 MHSA.attn_dropout=0.1（与设计相反）。
# ⚠ `--use-sdpa 1`（默认 1，显式留痕）：放开 CANN 融合 SDPA，相比手写 math 大幅降
#   注意力开销，且内部 fp32 累加比 fp16 手写 math 更不易溢出。受 batch 上限保护
#   （B>60000 自动回退 math），旧 CANN / 缺 SDPA API 时也自动回退。0 = 强制全走 math。
# ⚠ `--attn-online` **默认不给**：online-softmax 注意力数值等价但**非逐位相同**
#   （fp32 max|Δ|≈7e-07），开了会让 12 通道 bit-identical 基线失效；真机加速比未实测。
# ⚙️ **调优开关一律是 CLI 参数，没有环境变量**（2026-10-06 全部搬完；`GOAI_PROFILE`
#   是唯一例外——诊断开关，语义是「从第 N 步抓 50 步 kernel 表」）。五个总闸都是
#   **只慢不坏**（数值口径不变），出问题置 0 即回到已验证配置：
#     --use-sdpa 1|0        NPU 注意力走 CANN 融合 SDPA（默认 1）
#     --npu-sfa 1|0         融合注意力 SFA/PFA，优先于 SDPA（默认 1；探针+自检+回退）
#     --npu-swiglu 1|0      融合 SwiGLU（默认 1）
#     --npu-channels-last   NPU 卷积 NHWC（**默认 0**；走 torch_npu.npu_format_cast，
#                           非 torch.channels_last，见下方详注；失败自动降级）
#     --attn-query-chunk N  math 注意力 query 分块（默认 64；只影响 math 路径）
#     --attn-chunk-ckpt 1|0 math 注意力逐块检查点（默认 1）
# ⚠ `--use-checkpoint` 已归档：由 `KATAGO_SE_CFG['grad_checkpoint']` 决定，唯一关闭
#   路径是 `--compile 1`（而 NPU 上 --compile 无效）。别传它。
# ✅ eval 特征预取池（2026-10-06）：eval 的梯子特征曾是主进程串行计算，10 万行磨
#   25-30 分钟（NPU 归零、无日志，两次被当成挂死）。现在与训练预取器同点 fork 一个
#   2-4 worker 的 eval 池（augment=False，指标逐位不变），墙钟 ÷ worker 数；
#   启动日志锚点：`[data] eval 预取池已启用`。仍建议配 `--eval-max-batches 5`。
# ⚠ `--npu-graph-compile 1` 与梯度检查点**互斥**：开图编译会强制关 GC
#   （日志有 warning），显存/样本从 4.65 MB 涨到 ~278 MB ⇒ batch 上限 200 出头，
#   batch 1500/5500 必 OOM（2026-10-06 实测）。要试图编译：batch 180 + accum 8。
#   Linear-only（非整图）由 tests/test_npu_graph_compile.py 钉住。
# ⚠ `--npu-channels-last 1`：**不是** `torch.channels_last`（2026-10-07 探针定论）：
#   本机 torch 2.1.0 + torch_npu 2.1.0.post10 上，`torch.channels_last` 整条路不通 ——
#     · `model.to(memory_format=…)` → `Only contiguous_format or preserve_format is supported.`
#     · 逐参数 `.contiguous(memory_format=…)` → `NPU contiguous operator only supportted
#       contiguous memory format` (ERR01007 OPS feature not supported)
#   但**布局控制本身是有的**：`scripts/probe_npu_layout.py` 实测 ⇒
#     · `torch_npu.npu_format_cast` 存在，**只能用整数 aclFormat 调用**（枚举
#       `torch_npu.Format` 在该版本上不存在，引用它会 AttributeError）
#     · `npu_format_cast(x, 1)` 之后 `get_npu_format(x)` 由 0 → **1（NHWC）**
#   故代码走整数 aclFormat（NHWC=1），并在转完后**读回校验** format 真的是 1 ——
#   转换「声称」成功不算数（静默不生效时日志照样说「已启用」，而布局没变）。
#   转换失败自动降级回默认布局 + warning，训练照常（只少这项优化），不会崩。
#   启动日志锚点：`[model] channels_last 逐参数转换: N 个 4D 权重 | … | 入口=…`
#   ⚠ **收益仍未实测**：转成了不等于更快。要用 `speed_per_card` 与
#   `--npu-channels-last 0` 同配置对比，别只看这行日志就下结论。
#   换机器/换版本后先跑 `python scripts/probe_npu_layout.py` 确认入口还在。
# ✅ AdamW：NPU 上优先 `torch_npu.optim.NpuFusedAdamW`（post10 实测可用，日志
#   `已启用 fused AdamW (backend=npu)`）；不可用自动回退 standard+foreach。
#   C 段启动若卡在 [device] 之后：先 py-spy dump——大概率是 V7PackedDataset
#   读 37.6GB 分片的静默加载期（无日志），不是挂死。

# --- A-2  2 卡 910A（每卡 6000，accum 1 ⇒ 有效 12000，LR 0.00780 =
#          0.00356×√(12000/2500)）---
# ⚠ weight-decay 必须是 **0.0001**。2026-10-07 修正：本行原先误写 0.05（代码默认
#   与其余全部段都是 1e-4），是它的 **500 倍**，后果有两个且都很难一眼看出：
#     1) 日志里的 `loss` 是**报告口径** `log_loss = 真实加权损失 + l2_report`，
#        其中 `l2_report = c·‖θ‖²`、**c 就是 --weight-decay**。V7 初值 ‖θ‖²≈77835，
#        wd=0.05 ⇒ l2_report≈3892，而四项真实加权和只有约 7.8。实测日志
#        `loss=3541` **几乎全是那一项**，于是总 loss 平得看不出任何训练进展。
#     2) 优化器里是**真的**按 0.05 衰减：每步衰减 lr·wd，Σlr≈11 ⇒ 全程权重缩到
#        exp(-0.55)≈58%，value head 因独立高 LR 衰减得更狠。
torchrun --nproc_per_node=2 scripts/train_sft.py \
  --data data/sgf_19x19_full.npz --v7 1 --device npu --board-size 19 \
  --games-npz data/labels/games.npz \
  --batch-size 6000 --epochs 1 --lr 0.00780 --weight-decay 0.0001 \
  --gradient-accumulation-steps 1 --use-amp 1 --use-ema 1 \
  --use-sdpa 1 --attention-dropout 0 \
  --prefetch-workers 4 --prefetch-depth 16 \
  --log-every 5 --eval-every 25 --save-every 10 \
  --early-stop 1 --early-stop-patience 3 \
  --out models/a_v7_npu2.pth --swanlab 1 --ver a_v7.3_npu2 --swanlab-every 5

# --- B 段：+ KataGo 软标签（承接 A-2，2 卡）---

# 每条曲线「哪边好 + 终点在哪」：
#   ↓ 好：loss / policy_loss / value_loss / loss_v7/* / eval_kl / eval_brier
#         —— 但有地板：软 CE 的 policy 项下界是 H(soft)≈0.8，不是 0；
#            eval_kl 的 0 = 模型分布与目标分布完全一致（B/C 真收敛判据）。
#   ↑ 好：train_top1（A 段天花板 ~0.30-0.45=人类选择方差；B/C 软 argmax ~0.59
#         =KataGo-人类一致率）、eval_top1（诚实指标）、value_acc3（随机 1/3）。
#   过头也是病：policy_entropy ↓ 好但**地板不是 0**——正确终点是逼近
#         label_entropy(≈0.8)，即模型锐度追平目标分布；压得远低于它 = 过度自信。
#   看形状不看方向：lr（warmup 升→cosine 降，长得像计划就行）、
#         label_entropy（目标的属性，B/C 恒 ≈0.8 平线；A 段不产出）、
#         soft_row_frac（恒 1.0；掉 = 软标签采样坏了）、skip_rate_pct（恒 0）、
#         grad_norm（平稳即可，尖峰才是信号）、memory_gb（平台稳=健康，
#         逐 eval 点阶梯爬升=碎片/泄漏）、speed_per_card（台阶下降=数据侧问题）。
# 🔴 跨段不可比：目标口径 one-hot → 软分布换了，同值含义完全不同

# `loss_v7/*` 只上报**权重非 0** 的项（段 A 即 policy/policy_opp/value/futurepos
#   4 条）；权重表在 config 的 `run/loss_coef/*`，恒 0 平线不再上曲线。
# 🔴 eval 覆盖度看 `run/eval_max_batches`：只算 5 批的 top1 噪声大，别和跑满的比。

# ---------- 7. 已知失败与原因 ----------
# 权重键名/形状不匹配  ⇐ 12/22 通道混用；GoAI 的 stem 形状错会变 RuntimeError（不静默）

# fp16 前向 NaN       ⇐ 910A 走 fp16 时 CANN 融合内核处 65504 溢出 ⇒ 用 BF16 路径
# SwiGLU 融合刷警告   ⇐ 紧急开关 `--npu-swiglu 0` 退标准路径（默认融合）
# eval 慢/NPU 归零    ⇐ 已池化（eval 预取池）；仍慢就减 --eval-max-batches
# 全局特征异常 = 32.5  ⇐ foxpro 无 KM[650] 处（100 局里 1.62%），需加 --no-komi-outlier-fix
# ImportError: scipy   ⇐ requirements.txt 漏了
# sidecar 匹配率 <100%  ⇐ 未匹配的行权重置 0，训练自动忽略，不会静默丢数据
