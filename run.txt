# 硬件前提 —— **两条链路，别混**（2026-10-08 起）：
#
#   | 链路 | 入口            | 硬件          | 精度              |
#   |------|-----------------|---------------|-------------------|
#   | SFT  | train_sft.py    | **A100 40G 单卡** | BF16，无 GradScaler |
#   | RL   | selfplay_train.py | Ascend NPU   | **FP16 + GradScaler** |
#
# ---- SFT：A100 40G 单卡（本节 A/B/C 全部命令）----
#   `train_sft.py` 的 `_backend == 'cuda' and compute_cap >= (8,0)` 分支（唯一事实源）
#   自动给：BF16 + `use_scaler=False` + `channels_last=True` + `sdpa_force_math=False`
#   （⇒ FlashAttn 优先，回退内置 SDPA）+ TF32（`set_float32_matmul_precision('high')`）
#   + fused AdamW + `--compile` 按设备自动开 1。
#   ⇒ **`--scaler-init-scale` / `--scaler-growth-interval` 在 SFT 上是死参数**
#     （GradScaler 根本不会被创建），下面所有 SFT 命令都不给它们。
#     与 NPU 的 910B 路径不同：A100 是 Ampere+，BF16 原生支持，不需要 scaler。
#   ⇒ `--compile` **不给即可**（自动开）。要关就显式 `--compile 0`。
#     启动日志看两行：`[device] --compile 未指定 ⇒ 按设备自动取 1` 与 `[train] 已启用 torch.compile 算子融合`。
#   ⚠ `--compile` 与梯度检查点默认**二选一**（开 compile 就强制 `_gc = 0`）。
#     40G 卡上那等于「要融合就得把 batch 调小到吃不满算力」，而 batch 缩小吃掉的
#     吞吐通常远大于融合省下的 ⇒ **SFT 命令一律加 `--gc-with-compile 1`**（两者共存）。
#     前提已就位：检查点走 `use_reentrant=False`（`backbone._checkpointed`），
#     与整模型 `torch.compile` 兼容；且 V7 的 head 原来返回 dict、穿不过 checkpoint
#     的问题已修（`katago_v7._ckpt`，回归测试
#     `tests/test_katago_v7_grad_checkpointing.py::test_grad_checkpoint_survives_aot_autograd`）。
#     ⚠ 这条**不适用于** `--npu-graph-compile`（逐 Linear 编译的产物落在检查点段内部，
#       真的互斥，`--gc-with-compile` 对它无效；判据见 `train_sft.resolve_grad_checkpoint`）。
#   ⚠ `--compile-mode max-autotune` 与 `reduce-overhead` 都**带 CUDA Graphs**，
#     私有内存池不归还 ⇒ 40G 卡上长跑容易吃满显存。要自动调优就用
#     `--compile-mode max-autotune-no-cudagraphs`（新选项）。
#   ⚠ flash-attn 需 `pip install flash-attn`；加载失败**自动回退内置 SDPA**，
#     只少速度不会崩。`--flash-attn 0` 可强制禁用。启动日志看 `[env]` 那行。
#   ⚠ 「设备初始化之前」这条不变量：A100 首次启动时崩过一次
#     `RuntimeError: _BatchPrefetcher 不能在 torch.cuda 初始化之后构造`。
#     报错指的位置**不是真正原因** —— 预取器一直就在 `init_process_group` 之前，
#     真正原因是启动期那行环境诊断调了 `torch.cuda.get_device_properties(0)`
#     （它会建 CUDA context），诊断打完才构造预取器，撞上自己的护栏。
#     在 NPU 机上 `torch.cuda.is_available()` 为 False、整个分支跳过 ⇒ 潜伏的
#     CUDA-only 缺陷。已改为走 NVML（`nvidia-smi`）读型号/算力/空闲显存。
#     回归测试 `tests/test_prefetch_fork_ordering.py` 用 AST 锁这条顺序不变量。
#
# ---- RL：仍在 NPU，且是 FP16（见第 3 节）----
#   型号判据在 `train_sft.py` 的 `_backend == 'npu'` 分支：
#     命中 FP16 + GradScaler：名字含 `910B` / `910Pro` / `910-2`
#     其余（含 910C）：BF16、无 GradScaler
#   ⚠ RL 走的是 `selfplay_train.py`，它**自己**用 `torch.npu.amp.GradScaler`（:958）
#     且 `maybe_autocast` 默认 float16 ⇒ RL 侧恒为 FP16 + GradScaler，与 SFT 那套
#     BF16 口径**不同**，两条链路的 `--scaler-*` 语义不要互相套用。
#   ⚠ NPU 上 inductor 无效：`--compile` 在 NPU 被忽略（图编译走 `--npu-graph-compile`）。

# ---------- 2. ★ A → B → C：三段 SFT（同一个 22 通道 V7 模型，只换数据）----------
# ============================================================================
# 🔴 三段**共用一个模型**，权重用 `--model` 逐段承接（strict 零缺失）：
#   A 段 board 级 full.npz（人类着法 one-hot）
#     → B 段同一份 full.npz + soft_index（KataGo 软 CE）
#       → C 段 data/stdata/ 分片（搜索分布内建）
#   由 `tests/test_v7_single_model.py::test_weights_carry_from_board_level_to_packed_stage` 钉住。
#   A/B 能用 V7 的原因：`--v7 1` 按**数据布局**分派 —— 含 spatial_packed → V7PackedDataset，
#   含 boards → V7Dataset（实时算 22 平面）。两者喂模型的张量形状逐位相同 ⇒ 权重可承接。
#
# ⚠ 逐段**必须**显式 `--model` 承接，不要指望自动续训：三段 policy 口径不同
#   （one-hot → 软 CE → stdata 软 CE + value/futurepos/ownership），LR/epoch 各自独立。
# ⚠ A/B 段**必须** `--games-npz`：不给 ⇒ 贴目按 0 ⇒ 全局 ch5（currentSelfKomi/20）
#   恒 0、ch18 三角波走偏。19 维里有 2 维依赖贴目，sidecar 里 90.30% 的局有真贴目，
#   不接等于扔掉 9 成信息，**且不报任何错**（loss 照降、指标照报）。
# ⚠ B 段**必须** `--soft-only-sampling 1`：软 CE 是逐行二选一，不加则只有约 1% 的行
#   吃软标签、99% 喂 0，policy 去折中而不是学搜索。`--soft-weight 0` 关不掉这个问题。
# ⚠ C 段**不要** `--games-npz`（贴目已在行里）、也**不需要** `--soft-index`
#   （stdata 每行自带 policy_player_prob/policy_opp_prob，归一化即软标签）。
# ⚠ 落盘带 `.latest`：`--out models/x.pth` ⇒ 实际是 `models/x.pth.latest`。
#
# ---- 参数为什么是这些值 ----
# LR = 0.00356 × √(有效batch / 2500)，有效batch = batch × 卡数 × accum。
#   SFT 现在是**单卡 A100** ⇒ 卡数 = 1，于是 LR 只跟 batch 走：
#     1400 → 0.00267 ｜ 2000 → 0.00320 ｜ 2800 → 0.00377 ｜ 5600 → 0.00533
#   ⚠ **改 batch 必须按这条公式重算 LR**，别沿用上一段的旧值。
# batch：V7 的 22 通道特征在训练时**不再实时计算**（分片里已预算并位打包），
#   iterLadders 那 99.8% 的 CPU 开销在 V7 上不存在 ⇒ batch 可比 12 通道大。
#   预取 worker 是**每 rank** 的：单卡 ⇒ 给 24（旧实测的 CPU 甜点，总量不变）。
# ⚠ `--scaler-init-scale` / `--scaler-growth-interval` 在 **SFT（A100）上是死参数**：
#   A100 是 Ampere+，走 BF16、`use_scaler=False`，GradScaler 根本不会被创建。
#   ⚠ **RL（NPU）不同**：RL 走 `selfplay_train.py`，恒为 FP16 + GradScaler，
#     scaler 参数在那条链路上是真参数；旧记录里「910A 走 FP16 时不给就是代码默认
#     0.0 = PyTorch 的 65536，大 batch 下必炸（fp16 未来点平方溢出 65504）」，
#     需要时给 `--scaler-init-scale 1024 --scaler-growth-interval 100000`
#     （growth 调大 = 关掉自动增益，防震荡）。
#   启动日志里 `[启动] amp_dtype=… scaler=…` 那行会直接告诉你走的是哪条 —— 别靠猜。
# 🔴 `--attention-dropout 0` **必须显式给**（代码默认 0.1）：
#   0.1 是 12 通道 SE 网的默认值，会经 `train_sft.py` 透传进 V7，覆盖掉
#   `NBT_TF_CFG['attn_dropout']=0.0`——而 katago_v7.py 明确写「**没有 dropout**」。
#   实测：不给该 flag 时 MHSA.attn_dropout=0.1（与设计相反）。
# ⚠ `--use-sdpa 1`（默认 1）：`0` 强制回退手写 math 注意力。**A100 上默认就已经
#   走融合路径**（CUDA 分支直接 `sdpa_force_math=False` ⇒ FlashAttn 优先、回退内置
#   SDPA），所以这条在 SFT 上基本不用给；给 0 是「关掉融合注意力做数值对拍」用的。
# ⚠ `--attn-online` **默认不给**：online-softmax 注意力数值等价但**非逐位相同**
#   （fp32 max|Δ|≈7e-07），开了会让 12 通道 bit-identical 基线失效；真机加速比未实测。
#   且它只作用于**手写 math 路径** —— A100 上注意力走融合内核，给了也不生效。
# ⚙️ **调优开关一律是 CLI 参数，没有环境变量**（2026-10-06 全部搬完；`GOAI_PROFILE`
#   与 `GOAI_PROFILE_STEPS` 是仅有的例外——两个都是诊断开关、与训练配置无关，语义是
#   「从第 N 步抓 M 步 kernel 表」，M 默认 50；`M=0` = 起点即终点，在起点后的**第一个**
#   打点步就出表 ⇒ 配 `--log-every 5` 用 `GOAI_PROFILE=5 GOAI_PROFILE_STEPS=0`
#   即「第 5 步出表」，不必等满 50 步）。总闸都是
#   **只慢不坏**（数值口径不变），出问题置 0 即回到已验证配置。
#   **A100/SFT 上有意义的是下面这组**，其后是 NPU 专用、在 CUDA 上是死参数：
#     --flash-attn 1|0      融合注意力独立库（默认 1=自动优先；加载失败回退内置 SDPA）
#     --compile 1|0         inductor 算子融合（**不给=按设备自动**，A100 上自动 1）
#     --compile-mode ...    见第 0 节；A100 上别用带 CUDA Graphs 的两个值
#     --gc-with-compile 1|0 compile 与梯度检查点共存（默认 0；**SFT 建议给 1**）
#     --use-sdpa 1|0        0 = 强制回退手写 math（默认 1）
#     --use-checkpoint      **已归档**，别传（见下）
#   以下四个**只对 NPU/RL 有意义**，SFT 命令里给了不起作用：
#     --npu-sfa 1|0         融合注意力 SFA/PFA，优先于 SDPA（默认 1；探针+自检+回退）
#     --npu-swiglu 1|0      融合 SwiGLU（默认 1）
#     --npu-channels-last   NPU 卷积 NHWC（**默认 1**；走 torch_npu.npu_format_cast，
#                           非 torch.channels_last，见下方详注；失败自动降级）
#     --attn-query-chunk N  math 注意力 query 分块（默认 64；只影响 math 路径）
#     --attn-chunk-ckpt 1|0 math 注意力逐块检查点（默认 1）
# ⚠ `--use-checkpoint` 已归档：由 `KATAGO_SE_CFG['grad_checkpoint']` 决定。唯一让
#   它让位的路径是 `--compile 1`（且不给 `--gc-with-compile 1`）。别传它。
# ✅ eval 特征预取池（2026-10-06）：eval 的梯子特征曾是主进程串行计算，10 万行磨
#   25-30 分钟（GPU 归零、无日志，两次被当成挂死）。现在与训练预取器同点 fork 一个
#   2-4 worker 的 eval 池（augment=False，指标逐位不变），墙钟 ÷ worker 数；
#   启动日志锚点：`[data] eval 预取池已启用`。仍建议配 `--eval-max-batches 5`。
# ⚠ `--npu-graph-compile 1`（**仅 NPU/RL**）与梯度检查点**互斥**：逐 Linear 编译的
#   产物落在检查点段内部，开图编译会强制关 GC（日志有 warning），且 `--gc-with-compile`
#   对它**无效**。Linear-only（非整图）由 tests/test_npu_graph_compile.py 钉住。
#   ⚠ 旧记录里「显存/样本从 4.65 MB 涨到 ~278 MB ⇒ batch 上限 200 出头」是 **NPU
#     口径**且三个数互相矛盾（12.67 / 4.65 / 277），**对 A100 一律不适用**。
#   SFT 侧要走图编译就用 `--compile`（整模型），它与 GC 可以共存。
# ⚠ `--npu-channels-last 1`（**仅 NPU**）**不是** `torch.channels_last`
#   （2026-10-07 探针定论）：
#   本机 torch 2.1.0 + torch_npu 2.1.0.post10 上，`torch.channels_last` 整条路不通 ——
#     · `model.to(memory_format=…)` → `Only contiguous_format or preserve_format is supported.`
#     · 逐参数 `.contiguous(memory_format=…)` → `NPU contiguous operator only supportted
#       contiguous memory format` (ERR01007 OPS feature not supported)
#   但**布局控制本身是有的**：`scripts/probe_npu_layout.py` 实测 ⇒
#     · `torch_npu.npu_format_cast` 存在，**只能用整数 aclFormat 调用**（枚举
#       `torch_npu.Format` 在该版本上不存在，引用它会 AttributeError）
#     · `npu_format_cast(x, 1)` 之后 `get_npu_format(x)` 由 0 → **1（NHWC）**
#   故代码走整数 aclFormat（NHWC=1），并在转完后**读回校验** format 真的是 1 ——
#   转换「声称」成功不算数（静默不生效时日志照样说「已启用」，而布局没变）。
#   转换失败自动降级回默认布局 + warning，训练照常（只少这项优化），不会崩。
#   启动日志锚点：`[model] channels_last 逐参数转换: N 个 4D 权重 | … | 入口=…`
#   ⚠ **收益仍未实测**：转成了不等于更快。要用 `speed_per_card` 与
#   `--npu-channels-last 0` 同配置对比，别只看这行日志就下结论。
#   换机器/换版本后先跑 `python scripts/probe_npu_layout.py` 确认入口还在。
#   📌 A100 上**不需要**这一摊：CUDA 分支自动 `use_channels_last=True` 并用标准
#   `torch.channels_last` 转换（`model.to(memory_format=…)` 在 CUDA 上是正常路径）。
# ✅ AdamW：CUDA 上用 `torch.optim.AdamW(..., fused=True)`（日志
#   `已启用 fused AdamW (backend=cuda)`）；NPU 上优先 `torch_npu.optim.NpuFusedAdamW`，
#   不可用自动回退 standard+foreach。
#   C 段启动若卡在 [device] 之后：先 py-spy dump——大概率是 V7PackedDataset
#   读 37.6GB 分片的静默加载期（无日志），不是挂死。

# --- A 段：board 级 full.npz（人类着法 one-hot），单卡 A100 40G ---
# ⚠ **batch 未定档，由你现场调**（2026-10-08：A100 40G 上还没测过上限）。
#   仓库里 `v7_batch_memory_advice` 的每样本 MB 三个数（4.65 / 12.67 / 277）全是
#   **910A/NPU 口径**，对 A100 不可信 —— 照它算出来的 batch 建议值会系统性偏。
#   调法：从 2800 起步（= 旧单卡 910A 的定档，作为同 LR 口径的锚），OOM 就减半；
#   稳定且 `memory_gb` 平台还有余量就往上加。**定档后把下面 B/C 的 `--batch-size`
#   与 LR 一起改掉**（LR 必须跟着 batch 走，见上面的公式）。
