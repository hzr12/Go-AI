# ②' 损失 / 日志键 / 输入通道（P4.3 · P4.5 · P4.5b · P4.8 · P4.13）

#
# 【1】日志三个键的含义（键名被 tests/test_huber_loss.py::
#      test_log_keys_unchanged 钉死，含义在 P4.5b 变过）
#   · policy_loss / value_loss —— 两个分项本身，**不含**任何 L2
#       （train_sft.py:2314 / :2318 各自的 compute_*_loss 调用）
#   · loss = log_loss = policy_loss + w·value_loss + c‖θ‖²
#       （compose_losses :1208-1210，:2346 组装，:2430 读标量，
#        :2472 写进 swanlab 的 "loss" 键）—— 这个键**含**报告用的 L2 项
#   · opt_loss = policy_loss + w·value_loss（:1208）是**唯一被 backward 的量**
#       （:2348），**不含** L2
#   · c‖θ‖² 由 compute_l2_report（:1213-1283）从 optimizer.param_groups 读回
#     --weight-decay 算出，只覆盖 weight_decay != 0 的组（no_decay 的 norm/bias
#     不算），返回纯 python float ⇒ 不进计算图。所以：
#       **日志里的 loss 不是被优化的目标**；只有 w==1（默认）时
#       loss − policy_loss − value_loss 才等于 c‖θ‖²，
#       w≠1 时还多出 (w−1)·value_loss 这一项。
#
# 【2】损失默认值（P4.5 / P4.5b；tests/test_huber_loss.py 25 项测试钉住）
#   · --policy-loss 默认 **ce**（曾短期默认 huber，已按用户裁决改回；:1575）
#   · --value-loss 默认 **huber**（:1589）；value loss 权重默认 **1.0**
#     （:1565 —— BCE 时代为平衡 policy/value 梯度加的 5.0 补偿已删）
#   · --huber-beta 默认 **0.5**（:1601，须 > 0，policy/value 两侧 huber 共用）
#   · **没有 --l2-coef 这个参数**（D1 不新增 CLI；test_no_new_cli_params 点名
#     封杀）。唯一实际正则是 AdamW 的解耦 weight decay，--weight-decay 默认
#     1e-4（:1507），它同时就是上面 L2 报告项的系数 c。
#   · 下面三条 SFT 命令都不传损失旗 ⇒ 跑的就是这套默认。
#   ⚠ 键名没变、含义变过（loss 多了 c‖θ‖²，policy 默认也由 huber 改回 ce）
#     ⇒ **跨新旧 run 的 loss / policy_loss 曲线不可直接比**；
#     top1 是纯 argmax 准确率（evaluate_top1 :459-502），不受损失口径影响。

# 【3】输入通道与两代 checkpoint（P4.3 / P4.8 / P4.13 / **P4.2**）
#   · GoBoard.feature_planes 默认返回 **17** 通道（go_rules.py:2406），批量版同为
#     17（:2534-2535）；n_channels 取 12..17 的**前缀**（_check_n_channels

#     12-16 是新增五格（眼位×2、气==2 的块掩码×2、劫禁点掩码）；
#     通道 8 = 合法点掩码（空点 ∧ 非自杀 ∧ 非 PSK 重复，**不含 PASS**）。
#   · **训练侧自 P4.2 起建 v21 = 17 通道**：train_sft 的建网改走 build_v21_net，
#     结构写死在 src/networks/alphanet.py 的 **V21_CFG**（in_channels=17、184 宽、
#     8 Res + 4 Mamba-2 + 2 Transformer + 2 CrossAttn + 1×1 out，主干

#     tests/test_v21_budget.py 钉住）；数据侧两处 SupervisedDataset 同步传

#     回归留的，只改一侧 = 第一个 batch 就形状错）。
#   · **旧结构旗全部归档（D1）**：--arch / --backbone-channels / --res-blocks /

# ⚠ 下面这行**结构 flag 全是归档项**（--backbone-channels / --res-blocks /

#   --use-checkpoint / --export-onnx）：D1 之下建出来的**一定是 v21**

  --data data/sgf_19x19_full.npz \
  --device npu --board-size 19 \
  --backbone-channels 192 --backbone-res-blocks 17 \
  --res-blocks 8 --convnext-blocks 4 --attn-blocks 5 \
  --value-channels 96 --value-res-blocks 8 \
  --policy-channels 128 --policy-layers 3 \
  --batch-size 2000 --epochs 1 \
  --lr 0.00637 --weight-decay 0.0001 \
  --attention-mode mix --num-attention-layers 4 --num-heads 4 \
  --attn-mode window_global --attn-window 5 \
  --attention-dropout 0.1 --label-smoothing 0.1 \
  --gradient-accumulation-steps 1 \
  --use-amp 1 --use-ema 1 \

# ------------------------------------------------------------------
# 【v21 显存上限】4 卡 910A（每卡 32 GiB）—— 2026-09-30 实测重标定
# ------------------------------------------------------------------
# 三个 OOM 根因（都是**可复算**的数字，不是猜测；详见 commit 741b051）：
#   1. MambaLTI 的 drive 整条物化：(B,T,H,P,N) 每样本 361×4×46×64×4B = 17.0 MB
#      ⇒ B=2000 时**一次就申请 31.67 GiB**（与云端报错逐位吻合）。梯度检查点
#      管不到它 —— 它是块内部临时量，重算还要再物化一次。
#   2. 扫描块内的 u/M/h 活到反向：按块物化只降**前向瞬时峰值**，bmm/mul 的
#      输入照样被 autograd 留住。fp16@B=2000 单个 MambaLTI 块 = 52.6 GiB
#      ⇒ 云端 `20.13 GiB already allocated` + `Tried to allocate 2.81 GiB`
#      （2.81 GiB ≈ 又一个块的 u）。
#   3. 预取 worker fork 晚于设备初始化：`mp.Process` 默认 fork，4 个 worker
#      各继承一份 CANN 上下文与显存映射 ⇒ PyTorch 只记 6.30 GiB 而卡上 94%、
#      AICore 0%（6.3 + 4×6 ≈ 30 GiB）。
# 三条修复后同一口径的保留量（fp16@B=2000 折算）：
#   前向结束仍需存活   8.78 GiB   （16 个块边界 + 抽头特征 + 两个头）
#   最重的一块重算     4.9 GiB   （MambaLTI，修复前 52.6；注意力约 4~6）
#   ⇒ 活跃峰值 ≈ 14~15 GiB，另加分配器缓存（实测 20.13 活跃时 reserved 26.98，
#     约 6.9 GiB 空洞）⇒ 实际占用 ≈ 21~23 GiB / 32 GiB
#
#   每卡 batch   有效 batch   投影占用      lr（=0.00356×√(有效/2500)）   判定
#   ─────────────────────────────────────────────────────────────────────────
#     1500         6000        ~16~18 GiB      0.00552                  稳（保底档）
#     2000         8000        ~21~23 GiB      0.00637                  ★首跑推荐
#     2500        10000        ~26~28 GiB      0.00712                  可试（未实测）
#     2800        11200        ~29~31 GiB      0.00754                  很紧（未实测）
#
# ⚠ 上表是**投影**，来源见上；三次 OOM 说明投影会错，所以按「低一档先跑通、
#   再一档一档往上」的方式用，不要直接拿 2800 起步。
# ⚠ 降 batch 必须同步降 lr（同一套平方根缩放律），否则 8000 有效 batch 配
#   2800 的 lr 会把早期训练打飞。
# ⚠ 别为了省显存去动 --attn-window（window_global 的显存 ∝ nW×(ws²+ng)，
#   ws 变小时 ng 暴涨）；也别关检查点（见根因 2，那不是检查点能救的东西）。
#
# 【预取器的硬约束】`--prefetch-workers > 1` 会在**设备初始化之前** fork
#   worker 进程（train_sft.py 里已加运行时护栏：设备已初始化就构造 ⇒ 直接抛
#   错）。这是根因 3 的修复，**顺序不要改回去**：fork 早于 CANN 才是安全的那
#   侧（反方向才是 HCCL 的危险区）。workers=1 等于关掉预取器。

# ============================================================
# 关键优化总结
# ============================================================
# 1. SGF 元数据加权：解析 PB/PW 等级，高质量棋谱更高权重
# 2. 手数比例软标签 (D)：tanh(score × alpha)，连续胜率
# 3. value 损失两口径：--value-loss {huber,mse}（默认 huber）+ --huber-beta；
#    BCE / winrates 自动切换分支已删（test_sft_has_no_bce_branch），见 ②' 节
# 4. ConvNeXt 风格：5x5 深度卷积 + LayerNorm + GELU (--arch convnext)
# 5. 混合架构 Backbone：ResBlock (局部) + ConvNeXt (感受野) + Attention (全局)
# 6. 动态 topk：早期8/中期16/后期32 (自动启用)
# 7. 动态 virtual_loss：早期2/中期6/后期12 (自动启用)
# 8. 策略剪枝：跳过 prior < 0.01 的候选
# 9. 多样化 rollout：4 种温度策略轮换 (--use-diverse-rollout)
# 10. ONNX 后端：CPU 推理 3-5x 提速
# 11. 进程级并行：8进程绕过 GIL
# 12. 异步流水线：生成与训练完全并行 (--async-pipeline)
# 13. SwanLab 实验跟踪：实时可视化训练指标 (--swanlab)
# 14. 梯度累积 (--grad-accum-steps)：摊薄优化器步开销；配 --lr 1.4~2 倍
# 15. 双缓冲 H2D（CUDA）：pinned 槽交替 + 每槽 CUDA Event，搬运与计算重叠
# 16. MCTS 回传向量化 (--mcts-vector-backup，默认 1)：visit/value_sum 走 numpy 批量
# 17. 落子虚影（WebUI）：鼠标悬停显示半透明棋子，判定与点击共用 hitTest
